# Конфликты адресов магазинов: как это работает и зачем

## Зачем это нужно

При импорте чеков один и тот же реальный магазин часто приходит с разными вариантами адреса:
- добавили номер терминала (`... 68`),
- указали «касса самообслуживания»,
- мелкие отличия в пробелах и пунктуации.

Для общих названий вроде `Аптека` это создаёт неоднозначность:
- по одному имени нельзя надёжно разделить магазины,
- но и отклонять валидный импорт на уровне роутера (`409`) не хотим.

Цель механизма:
1. валидный импорт чека всегда проходит,
2. чек привязывается к детерминированному магазину,
3. неоднозначность фиксируется как конфликт для отложенного ручного резолва,
4. решение пользователя запоминается для будущих импортов.

## Принципы

1. Импорт не падает из-за конфликта адреса.
   - Конфликты решаются в сервисном слое, не на уровне роутера.

2. Связи `чек -> конфликт` создаются только при реальном конфликте.
   - Не на каждый импорт.
   - Только когда имя совпало, а адрес не совпал.

3. Резолв асинхронный.
   - Пользователь может зайти позже и разрулить конфликт в UI.

4. Решение пользователя сохраняется явным правилом.
   - `(owner, normalized_name, normalized_address) -> shop_id`.

## Таблицы

### `shops`
Основная сущность магазина.
- `address` используется как текущий primary-адрес для отображения.

### `shop_addresses`
Алиасы адресов магазина (все встреченные варианты).
- `shop_id`
- `address_raw`
- `address_normalized`
- `is_primary`
- `seen_count`, `first_seen_at`, `last_seen_at`

Зачем:
- хранить историю вариантов адреса,
- показывать конфликты в интерфейсе,
- дать выбрать primary или вынести алиас в дубль магазина.

### `shop_address_rules`
Правила резолва для повторных импортов.
- `owner_id`
- `retail_name_normalized`
- `address_normalized`
- `shop_id`
- уникальность: `(owner_id, retail_name_normalized, address_normalized)`

Зачем:
- не создавать один и тот же конфликт повторно,
- после ручного решения сразу направлять новые чеки в нужный магазин.

### `receipt_shop_address_conflicts`
Связи чеков с нерешёнными конфликтами адресов.
- `owner_id`
- `receipt_id`
- `shop_id` (магазин, к которому чек был привязан в момент импорта)
- `shop_address_id` (конфликтный алиас адреса)
- уникальность: `(receipt_id, shop_address_id)`

Зачем:
- понимать, какие чеки были импортированы при нерешённом конфликте,
- при резолве массово и корректно поправлять `receipt.shop_id`.

## Алгоритм поиска/создания магазина (`match_or_create_shop`)

Вход: `owner_id`, `ShopCreate(retail_name, address, shop_owner_id)`.

Нормализация:
- имя: схлопывание пробелов + `casefold`,
- адрес: схлопывание пробелов + `casefold`.

Порядок поиска:
1. Точное совпадение в `shops` по `retail_name + address`.
2. Совпадение по правилу в `shop_address_rules`.
3. Совпадение по алиасам в `shop_addresses` (по нормализованному адресу + проверка имени).
4. Fallback по имени:
   - найден магазин с тем же нормализованным именем,
   - новый адрес добавляется как алиас,
   - этот алиас помечается как конфликтный (`conflict_alias_id`).
5. Если ничего не найдено: создаётся новый магазин + primary-алиас адреса.

Результат:
- `ShopMatchResult(shop, conflict_alias_id?)`.
- `conflict_alias_id` заполняется только в пункте 4.

## Поведение при импорте чека

Во время импорта raw JSON:
1. магазин определяется через `match_or_create_shop`,
2. чек создаётся обычным путём,
3. если есть `conflict_alias_id`, создаётся запись в `receipt_shop_address_conflicts`.

Важно:
- валидный чек не отклоняется из-за конфликта магазина,
- конфликт фиксируется и виден для последующего ручного резолва.

## Как работает резолв конфликта

### Действие: `Set Primary Address`
Сервис: `set_shop_primary_address`.

Что происходит:
1. выбранный алиас становится primary,
2. `shops.address` обновляется из этого алиаса,
3. создаётся/обновляется правило в `shop_address_rules`,
4. конфликтные связи по этому алиасу закрываются:
   - чеки (если нужно) привязываются к этому магазину,
   - записи в `receipt_shop_address_conflicts` удаляются.

### Действие: `Create Duplicate by Address`
Сервис: `split_shop_by_address_alias`.

Что происходит:
1. выбранный не-primary алиас переносится в целевой магазин (существующий дубль или новый),
2. у целевого магазина этот адрес становится primary,
3. создаётся/обновляется правило `name+address -> target_shop`,
4. конфликтные чеки перепривязываются на целевой магазин,
5. соответствующие записи конфликтов удаляются.

Ограничение:
- primary-алиас нельзя split-ить; сначала нужно выбрать другой primary.

## Почему связи с чеками пишем только при конфликте

Если писать `receipt -> alias` на каждый импорт:
- появится много шума в данных,
- при резолве можно затронуть чеки, где конфликта не было.

Поэтому связи создаются только в реальном конфликтном кейсе (`same-name fallback`).

## Почему правила всё равно нужны

Без правил после ручного резолва тот же конфликт будет появляться снова.
Правило фиксирует решение пользователя и делает поведение стабильным на следующих импортах.

Особенно критично для общих названий (`Аптека`, `Магазин` и т.д.).

## Известное ограничение

Автоматически не исправляются старые чеки, импортированные до появления механизма конфликтных связей.
Авто-исправление работает только для чеков, которые присутствуют в `receipt_shop_address_conflicts`.

Для остальных остаётся ручная смена магазина у чека в UI.

## Заметки по API/UI

- Импорт валидного чека остаётся успешным.
- В списке магазинов конфликт показывается через `has_address_conflict` (по количеству алиасов).
- В деталях магазина доступен список алиасов.
- Доступные действия в UI:
  - выбрать primary-адрес,
  - вынести адрес в дубль магазина,
  - вручную сменить магазин у конкретного чека.

## Ожидания по схеме БД

Для чистого развёртывания через `create_all` должны существовать таблицы:
- `shop_addresses`,
- `shop_address_rules`,
- `receipt_shop_address_conflicts`.

Если схема пересоздаётся с нуля и дальше грузятся сырые JSON-чеков, это корректный сценарий (ручные правки намеренно не восстанавливаются).
